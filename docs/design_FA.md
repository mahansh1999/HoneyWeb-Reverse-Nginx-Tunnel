# طراحی HoneyWeb Reverse Nginx Tunnel

> **وضعیت:** آزمایشگاه کامل شد (2026-11-05). هر سه روش روی یک جفت سرور ایران و آلمان نصب و اندازه‌گیری شدند (بخش ۵).
>
> **برچسب شاهد:** مثل پروژه اصلی.
> - **[Lab]** یعنی اندازه‌گیری در Network Namespace و نه مسیر واقعی.
> - **[برآورد]** و **[فرضیه]** هم به همین معنا به کار رفته‌اند.

## ۱. هدف

ارتباط بین سرور خارج و سرور ایران باید روی سیم شبیه این باشد: یک سرور خارجی دارد یک وب‌سایت ایرانی را باز می‌کند.

- سرور ایران یک وب‌سایت HTTPS ِ واقعی است: Nginx، گواهی Let's Encrypt و صفحه‌های معمولی.
- اتصال را همیشه سرور خارج شروع می‌کند. پس این یک تانل معکوس است.
- از iptables استفاده نمی‌شود.

## ۲. شکل کار

```
کاربر ──TLS──> Nginx ِ ایران :443  (سایت؛ Reverse Proxy ِ کاربر)
                 │  /channel و /tunnel/*  فقط با Token (Map ِ Nginx)
                 ▼
        موتور HoneyWeb Tunnel (wsmux) روی 127.0.0.1
                 ▲  Sessionهای Mux: Pool × mux_con Stream
                 │
   ── اینترنت ── TLS از Nginx ِ فنلاند (proxy_bind، SNI و Host ِ سایت، proxy_ssl_verify) ──
                 │
        موتور HoneyWeb Tunnel (wsmux) ──> 127.0.0.1:Nginx ِ فنلاند
                 │
                 └──> Xray روی 127.0.0.1 ِ فنلاند
```

- **دو Nginx ِ معمولی:** هسته Nginx تغییر نکرده است. Nginx فقط TLS و قاب HTTP/WebSocket را انجام می‌دهد. Mux را موتور HoneyWeb (wsmux) انجام می‌دهد که در Production امتحانش را داده است.
- **Route:**
  - یک مسیر WebSocket ِ سایت مستقیم وارد تانل می‌شود.
  - مثال: Host ِ پنل با یک Path ِ مخفی WebSocket.
  - Nginx ِ ایران آن را به یک پورت Loopback ِ تانل می‌دهد و فنلاند به Inbound ِ Xray می‌رساند.
  - Path به `/` بازنویسی می‌شود.
  - IP ِ واقعی کاربر در `X-Forwarded-For` به Xray می‌رسد [Lab].
- **پورت‌های دیگر:** پورت‌هایی که کاربران مستقیم استفاده می‌کنند، مثل 22281 و 8443، روی موتور ایران باز می‌شوند و از همان تانل به فنلاند می‌روند.

## ۳. چیزی که فایروال می‌بیند

| جزء | روی سیم | توضیح |
|---|---|---|
| اتصال | IP ِ خارج به IP ِ ایران روی 443 | جهت مثل «بازدیدکننده خارجی» است |
| TLS | SNI = دامنه سایت، گواهی معتبر LE | در TLS 1.3 گواهی رمز شده است |
| اثر انگشت Client | Nginx/OpenSSL (proxy_ssl) | شبیه سرور به سرور است، نه مرورگر. حالت جایگزین موتور، wssmux با uTLS Chrome، هم پشتیبانی می‌شود |
| داخل TLS | Upgrade ِ HTTP/1.1 به WebSocket، بعد smux | دیده نمی‌شود |
| Probe ِ فعال | سایت: 200. مسیر تانل بدون Token: 404، عیناً مثل صفحه ناموجود. پورت 80: Redirect و ACME | [Lab] |

**آنچه همچنان دیده می‌شود [فرضیه]:**
- تعداد زیاد اتصال طولانی از یک IP، به اندازه Pool؛
- حجم بالا؛
- الگوی Keepalive.

این‌ها ذات هر تانلی است. کاهششان (Pool ِ کوچک‌تر با mux_con ِ بزرگ‌تر، و غیره) با اندازه‌گیری انتخاب می‌شود.

## ۴. امنیت

- **Token:** در Map ِ Nginx (`auth.conf`، 0600 root) و در Configهای موتور (0640 root:hwtunnel). در هیچ خط فرمان یا Logی نمی‌آید.
- **Nginx ِ فنلاند گواهی ایران را چک می‌کند:**
  - `proxy_ssl_verify` با CA ِ سیستم و نام سایت.
  - کسی که وسط مسیر بنشیند (MITM) Token را نمی‌گیرد.
  - [Lab]: Exitی که CA ِ دیگری را قبول داشت حتی یک Session هم نگرفت.
- **موتور:** Token را در زمان ثابت مقایسه می‌کند. Map ِ Nginx فقط یک فیلتر اضافه جلوی آن است.
- **نکته موتور:** موتور Client ِ جدید با Token را «در جا» می‌پذیرد. پس Token باید فقط روی همین دو سرور باشد.
- **کلید `tls_verify`:** برای حالت wssmux کلید جدید `tls_verify` به موتور اضافه شد (Opt-in، Branch `feature/nginx-front`). بدون آن، `simple_auth` پشت Proxy ِ TLS Token را به هر کسی که Handshake را جواب دهد می‌داد.

## ۵. اندازه‌گیری [Lab]

شرایط آزمایشگاه:
- netem 40 ms در هر جهت، سقف 1 Gbit/s؛
- Pool 64 و mux_con 8؛
- Profile ِ Turbo؛
- هر طرف یک هسته.

داده خام در مخزن داخلی پروژه نگهداری می‌شود.

| | WSSMUX ِ فعلی | Nginx ِ ایران + Chrome | Nginx ↔ Nginx |
|---|---|---|---|
| دانلود ۸ / ۱ اتصال (Mbps) | 948 / 168 | 940 / 166 | 942 / 168 |
| آپلود ۸ / ۱ اتصال (Mbps) | 941 / 167 | 951 / 166 | 951 / 162 |
| Handshake ِ TLS ِ کاربر از داخل تانل، P50 | 85.2 ms | 86.4 ms | 86.1 ms |
| CPU ِ ایران، دانلود ۸ | 0.33 | 0.53 | 0.51 هسته |
| CPU ِ خارج، آپلود ۸ | 0.32 | 0.32 | 0.52 هسته |

- **سرعت و تأخیر:** برابرند. سقف سرعت سقف netem است.
- **هزینه:** حدود 50 تا 60 درصد CPU ِ بیشتر در هر طرف که Nginx در آن هست، به خاطر لایه TLS ِ Nginx.
- **نتیجه Lab:** این عددها سرعت مسیر واقعی نیستند.

## ۶. استقرار

- **ابزار:** `rnt.sh`:
  - `iran`، `kharej --via-nginx`، `acme`، `start`، `status`، `remove`؛
  - و `render-*` برای آزمایشگاه، که همان قالب‌های واقعی را تولید می‌کند.
- **حذف iptables** بدون قطعی (Make-before-break):
  1. اول تانل بالا می‌آید. یک استثنای موقت iptables فقط برای IP ِ مبدأ ِ تانل گذاشته می‌شود.
  2. بعد قانون‌های قدیمی با Backup و Restore ِ خودکار حذف می‌شوند.
  3. اتصال‌های باز تا پایانشان روی مسیر قدیم می‌مانند (conntrack).
- **ماندگاری:** `/etc/rc.local` اصلاح می‌شود تا iptables بعد از Reboot برنگردد.
- **گواهی:**
  - تا وقتی پورت 80 ِ ایران دست Nginx ِ خودش نیست، گواهی LE ِ همان نام از فنلاند موقتاً آورده می‌شود.
  - بعد ایران گواهی خودش را با HTTP-01 می‌گیرد.

## ۷. مانده

- تست روی مسیر واقعی، و مقایسه پایداری با WSSMUX ِ فعلی در ساعت اوج.
- برای Production ِ بلندمدت، یک دامنه خنثی بهتر است. دامنه‌ای که نام برند VPN در آن است مناسب نیست.
- اندازه Pool و Keepalive برای کمتر دیده شدن، پس از اندازه‌گیری.
- اگر لازم شد، ماژول اختصاصی Nginx. برای این کار طراحی جدا لازم است.
